# 问题空间与三层模型

网络同步不是单一算法。先把问题拆开，再选方案。

## 要对抗的四件事

| 约束 | 游戏里的表现 |
| --- | --- |
| 延迟 | 操作到反馈有空隙；远程物体“慢半拍” |
| 抖动 / 丢包 | 动作卡顿、瞬移、技能“打空” |
| 带宽 | 实体一多，全量状态发不起 |
| 信任 | 客户端不可信；透视、加速、改伤害都从这里来 |

玩家感知的“手感”主要吃延迟；服务器感知的“公平”主要吃权威与反作弊；运营成本主要吃带宽与服务器 CPU。

## 三层模型

每一层独立选择。混用时写清哪一层是哪一种，避免口头上说“我们用帧同步”，实际拓扑已经是 Dedicated Server。

### 1. 拓扑：机器怎么连

| 拓扑 | 谁跑模拟 | 适用 |
| --- | --- | --- |
| Dedicated Server | 独立服务器 | FPS、BR、MMO；反作弊强 |
| Listen Server | 其中一个玩家兼主机 | 合作 PVE、大厅房 |
| P2P | 各端直连，无中心权威 | 小规模、格斗、部分 RTS |
| Relay | 中继只转发，不模拟 | 打通 NAT；主机仍可能是玩家 |

当代线上对战默认 Dedicated Server。Listen Server 省成本，主机玩家拥有延迟优势。
P2P 省服务器，NAT 与作弊难处理。Steam Datagram Relay、Epic EOS、Photon 等把 Relay 做成基础设施。

### 2. 权威：谁说了算

| 模型 | 含义 | 代价 |
| --- | --- | --- |
| 服务器权威 | 服务器状态为真，客户端只是显示器 + 输入源 | 手感靠预测补 |
| 客户端权威 | 拥有者说了算，服务器转发 | 易于作弊；适合休闲、单机联机 |
| 共享权威 | 各端拥有自己的对象 | 冲突要额外协议 |

竞技与数值敏感玩法用服务器权威。预测、和解、滞后补偿都是在“服务器说了算”的前提下把手感做回去。

### 3. 协议：线上走什么数据

| 协议 | 传输内容 | 前提 |
| --- | --- | --- |
| 输入同步 | 玩家输入（按键、摇杆、指令） | 各端模拟必须确定 |
| 状态同步 | 位置、生命、动画、技能状态等 | 服务器（或主机）持有真状态 |
| 事件 / RPC | 一次性消息（开火、开门、扣费） | 可靠或不可靠通道分开设计 |
| 混合 | 不同字段走不同主线 | 每字段一个写入者；见 [schemes/hybrid/README.md](schemes/hybrid/README.md) |

帧同步 = 输入同步 + 确定性模拟。状态同步 = 状态快照 / 增量 + 非确定表现层。回滚 = 输入同步 + 乐观执行 + 存档重演。引擎复制 = 按对象切分的状态同步 + RPC。

## 一致性 vs 手感

分布式系统教科书追求强一致。游戏追求**可玩的一致**：

- 格斗需要帧级公平，愿意付回滚闪烁的代价。
- FPS 需要“我看到的就是我打到的”，用滞后补偿改写服务器判定时刻。
- RTS 能容忍 200ms 指令延迟，换带宽极低。
- MMO 容忍更长延迟，换万人同图。

没有全局最优。先定品类的延迟预算和作弊模型，再选协议。

## 时钟

所有方案都要回答“现在是第几帧 / 第几毫秒”。

| 做法 | 用途 |
| --- | --- |
| 固定 Tick（如 30 / 60 / 128 Hz） | 模拟步长恒定，便于确定性和补偿 |
| 渲染帧与模拟帧分离 | 高帧率显示，低频率联网 |
| 服务器时间戳 | 快照排序、插值、滞后补偿回放 |
| 输入编号（Sequence） | 预测和解、丢包重发、去重 |

客户端本地时钟会漂。用服务器时间做权威，客户端只估 RTT 与一程延迟。
