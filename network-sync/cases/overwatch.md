# 守望先锋

主线：**服务器权威的状态同步**，再叠「本地先演、服务器纠正」。

它不是帧同步：网上走的是状态结果，不是「十个人的按键集合」。
它也不是格斗游戏的 GGPO：回退只发生在你自己的英雄上，真值来自专用服务器，不是来自对端迟到的输入。

公开来源：Timothy Ford，GDC 2017，
*Overwatch Gameplay Architecture and Netcode*；
以及 *Networking Scripted Weapons and Abilities in Overwatch*。

## 先记住三句话

1. 谁赢了、谁受伤，以服务器为准。客户端改内存改不了结算。
2. 你自己的英雄在本地立刻动，为的是手感。服务器稍后确认或打回。
3. 别人的英雄是服务器状态复制过来的。你不负责「算对方这一枪打没打中」。

Ford 的原话方向：客户端不可信（*some clients are jerks*）。
预测是显示器，服务器才是裁判。

## 一局里各台机器干什么

| 机器 | 干什么 |
| --- | --- |
| Dedicated Server | 以固定步长模拟整张图；收输入；算伤害；把状态增量发给每个人 |
| 你的客户端 | 立刻按你的输入演自己的英雄；把输入发给服务器；用服务器结果纠正 |
| 别人的客户端 | 同样预测他们自己；对你则只显示服务器复制过来的你 |

12 个玩家，就有 12 份「对自己的预测」和 1 份服务器真值。
彼此看到的对方，都是稍微过去的复制，不是对方机器上的预测。

## 按一下开火：逐步发生什么

假设模拟步长 16ms（约 60Hz），你到服务器的一程延迟 80ms。

1. **0ms，你按下射击。**
   客户端马上播后坐、生成预测中的子弹或技能。你不感到等待。
2. **同一时刻，输入上行。**
   包里不是「只有这一帧」，而是从服务器上次确认过的移动状态起，之后每一帧的输入。
   这叫滑动窗口。中间丢一个包，下一个包仍带着缺口里的按键。
3. **约 80ms，服务器收到。**
   服务器在自己的时间里推进模拟：你的位置、弹药、技能状态、世界碰撞。
   命中不信你的准星截图，而用服务器世界（见下面「命中」）。
4. **再约 80ms，增量回到你。**
   包里是 Statescript / 移动等状态差，不是「请你自己再算一遍整局」。
5. **对得上：继续。**
   你的预测和服务器一致，画面不用改。这是常见情况。
6. **对不上：回退再演。**
   例如你以为自己在跑，服务器判定你已被眩晕。
   客户端丢弃那一段预测，套上服务器快照，用已缓存的后续输入重演到「现在」。
   多数时候平滑过去；偶尔火箭会消失——那是预测抛体的代价。

别人那边看不到你的预测。他们看到的是服务器已经确认、再复制过去的你。

## 时钟

模拟必须 60Hz。渲染可以 30fps，那一帧就连续跑两个模拟步。
模拟比渲染便宜，所以这做得到。服务器如果跟不上，会进入死亡螺旋：
晚一帧 → 下一帧要补更多步 → 更晚。所以 60Hz 是硬约束，不是「尽量 60」。

客户端的「现在」比服务器超前约 `RTT/2 + 1` 个缓冲帧。
RTT 160ms 时大约超前 96ms。这不是穿越：
你的输入先在本地落地，数据包还在路上，服务器尚未看见这一帧。

## 输入怎么抗丢包

两套一起用。

**滑动窗口。** 每次把「尚未被服务器确认」的输入整段带上。
按键多半是按住 WASD，不是每秒点 60 次，所以很好压。来自 QuakeWorld。

**时间膨胀。** 服务器发现输入快断了（包没到，要拿上一帧顶上），就通知客户端：
把 16ms 步长略缩到约 15.2ms，本地稍快，把输入缓冲灌满。
稳定后再反向变慢，把缓冲抽干。反馈一直在跑，玩家不应感到变速。

TCP 的重传和慢启动不适合这种 60Hz 输入。他们走 UDP，可靠性自己做。

## 预测什么、不预测什么

多数射击只预测自己走路。守望先锋默认预测三件事：**移动、武器、技能**。
某技能不想预测，要显式退出，而不是显式打开。

法老之鹰的火箭也预测。当时其他工作室的 GDC 劝过：大体积抛体一旦预测错，玩家会看见火箭蒸发。
Ford 的结论：手感值得。论坛偶有帖子，他们接受。

预测错时的「rollback」只作用在本地实体上。不要和格斗网码混名：

| | 守望先锋这里的回退 | 格斗 GGPO |
| --- | --- | --- |
| 回退对象 | 你自己的英雄 | 整局确定性世界 |
| 对齐的真值 | 服务器快照 | 对端迟到的真实输入 |
| 网上主要走什么 | 状态增量 + 你的输入 | 所有人的输入 |
| 别人怎么来的 | 复制服务器状态 | 你按他的输入在本地重演 |

## 命中怎么算

你开火时，你准星上的敌人是你客户端插值/预测出来的画面，比服务器「现在」更旧。
若服务器用「此刻」的敌人位置判定，你会经常打空已经看见的人。

服务器做法：把相关世界倒带到**射击者当时看见的那一时刻**，再打射线。
这叫滞后补偿 / 回绕。被打到的人可能感觉「我已经进掩体了」。

为省 CPU，不是 12 人全图都倒带。先用大约半秒位移扫过的包围体和射线做粗测，
只有可能挨打的实体才精确回绕。

RTT 大约超过 220ms 时，关掉这种「按你所见判定」，改外推敌人位置。
窗口太大，等于允许高延迟玩家射击过去。这是公平夹子，不是精度优化。

## 技能如何规模化：Statescript 和 ECS

英雄技能是状态机：充能、引导、抛体、护盾、取消。
这些跑在自研视觉脚本 Statescript 上。预测、复制、确认由运行时自动做，
设计师少写「这是网络变量吗」这种分支。新英雄主要是新图，不是新协议。

底层是 ECS：实体是 ID，组件是数据，系统是逻辑。
生产期大约 46 个客户端系统、103 种组件，真正碰玩法联网的只有三套：
**移动、武器、Statescript**。英雄增加，联网代码面不跟着线性变宽。

远端英雄的高层脚本有时间预算（Ford 提到约 1.5ms 量级），尖峰抹掉。
你的机器把 CPU 花在预测你自己；别人不必按本地精度全算一遍。

## 为什么不能改成王者那种帧同步

守望先锋要准星、扫射、瞬发、抛体、可破坏和移动平台（车上造塔）。
这些要服务器物理和服务器命中，并且要能惩罚改客户端的人。

若改成「只广播 12 人输入、各端自算」：

- 等齐输入或乐观丢输入，射击都会糊。
- 完整世界在本地，透视和自瞄面变大。
- 命中争议没有服务器这份可回退的真值。

他们把确定性用在「重演自己的预测」，不用在「十二台机器算同一份世界」。

## 能抄什么、不能抄什么

能抄：技能射击默认预测、个别退出；联网收敛到少数系统；命中回绕必须封顶；
输入窗口 + 时间膨胀，不要指望 TCP。

不能抄：把这里的 rollback 当成整局 GGPO 去实现。
